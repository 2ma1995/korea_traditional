## 1. 세 층

| **3층** | 다음엔 뭐가 나와? | NEXT | 절기마다 후보 셋에 청약한다. 1위가 실제로 상장(출시·재입고)된다 |

## 2. 하루

국장이 닫히는 그 순간에 빵장이 연다. 그것이 서비스 이름이고 전제다.

```
09:00  국장 개장     차트가 30초마다 살아 움직인다
15:30  국장 마감     오늘 등락 확정 → 오늘의 폭 확정
   │
   └── 15:30  빵장 개장   오늘의 빵을 한정 수량으로
24:00  빵장 마감
```

코드값 — `OPEN 15:30` · `CLOSE 24:00` · `ALWAYS_OPEN = false`(실제 시간을 지킨다)
주식시장이 쉬는 날은 빵장도 쉰다.

## 3. 가격

네 축의 덧셈이다. **규칙 자체의 최대가 기업 확인 상한(38%)과 같아서** 잘라낼 필요가 없다.

```
구간 기본   최대 30%   ← KOSPI 변동폭
하락장      +3%p      ← KOSPI 방향
수요        +3%p      ← SKU별 · 담아만 두고 안 사는 빵
재고        +2%p      ← SKU별 · 판매속도 대비 며칠치
──────────────────────
합계 최대   38%
```

### 구간 경계는 5년 실측으로 잡았다

| KOSPI 절대 변동폭 | 상승·보합 | 하락 +3%p | 빈도 | 연 환산 |
|---|---:|---:|---:|---:|
| 0.3% 미만 | 5% | **8%** | 22.2% | 55일 |
| 0.3 ~ 0.8% | 10% | **13%** | 28.1% | 69일 |
| 0.8 ~ 1.5% | 15% | **18%** | 26.4% | 65일 |
| 1.5 ~ 2.5% | 20% | **23%** | 14.0% | 35일 |
| 2.5% 이상 | 30% | **33%** | 9.3% | 23일 |

- 아래 세 구간이 22 / 28 / 26%로 고르게 나뉘어 **열흘 중 여드레는 폭이 서로 다르다**
- 기본 기대값 **13.5%** → 하락 보정 포함 **14.7%**
- 상한 38%는 안전장치로 **5년간 도달일 0일** (실측 최대 33%)

**검증** — Yahoo `^KS11` 일봉 5년 **1,219 거래일** 직접 집계 · 평균 일간 변동 **1.16%** · 하락 41.5% / 상승 50.4% / 보합 8.1%

### 방향은 기분도 정한다

| 마감 | 이름 | 메시지 |
|---|---|---|
| ▲ 상승 | **자축가** Celebrate | 오르는 날엔 빵값도 내립니다. 함께 축하해요 |
| ▼ 하락 | **위로가** Comfort `+3%p` | 쓸쓸한 마감, 달콤하게 마무리해요 |
| — 보합 | **본전가** Steady | 잔잔한 하루. 그래도 빵장은 열립니다 |

## 4. 구매

누르면 **예약**이 된다. **결제가 아니다.**
서버는 클라이언트가 보낸 값을 믿지 않고 네 가지를 다시 계산한다.

```
[ 8,470원에 구매하기 ]
   │  POST /api/fill { productNo, depth }
   ▼
① 개장 여부    marketHours()
② 폭 일치      rateFor(오늘 등락)
③ 재고         /api/stock — 자사몰 실시간
④ 선착순 자리  tryFill — slot 1~30
   ▼
"예약됐습니다 · N번째"  +  🗳 청약권 1장
   ▼
"자사몰에서 결제하기 ↗"   ← ⚠️ 여기서 정가가 뜬다
```

우리에게 결제 수단이 없다. 판매·결제는 카페24(makji.kr)가 한다.
**그래서 오늘 가격을 카페24에 반영하지 않으면 화면이 거짓말이 된다.**

## 5. 공모

다음에 나올 빵을 손님이 청약으로 정한다. 레시피 콘테스트를 폐기하고 이것으로 갈았다 — **참여는 탭 한 번, 보상은 실제 출시**다.

| 항목 | 내용 |
|---|---|
| 주기 | 절기마다 (약 15일). 한 회차가 끝나면 바로 다음이 열려 빈 기간이 없다 |
| 모드 | **이분이지**(춘분·하지·추분·동지) 연 4회 = 신제품 공모 · 나머지 **20회 = 재입고 공모** |
| 재입고 후보 | 자사몰에서 지금 품절인 상품 중 정가 높은 순 셋. 1위가 들어오면 목록에서 빠져 **스스로 돈다** |
| 청약 자격 | **오늘 빵을 산 사람만 1장.** 구매가 증거금 역할 — 무료 탭이면 투표지 공모가 아니다 |
| 검증 | 로그인이 없어 서버 발급 HttpOnly 쿠키로 확인. 쿠키를 지우면 재획득 가능하나 구매가 선착순 한정이라 비용이 든다 |
| 상장 | 절기 당일 경쟁률 1위 |

기업 개발 부담을 **연 4회**로 묶은 것이 핵심이다. 평소엔 이미 있는 제품을 다시 들여오는 것이라 **지킬 수 있는 약속**이 된다.

## 7. 근거

*"코스피랑 빵값이 무슨 상관이냐"* 에 대한 답이다. **원가 인과는 만들지 않는다** — 코스피는 **수요 지표**로 쓴다.

> 코스피가 빵 원가를 바꾸지는 않습니다.
> 하지만 **국장이 흔들린 날은 소비가 위축되는 날**이고, 저희는 그날 **재고를 돕니다.**

| 주장 | 근거 | 수준 |
|---|---|---|
| **왜 코스피인가** | Han (2026) *Global Economic Review* 55(1) — 서울 **일별 카드결제 데이터**와 코스피 일별 수익률의 정(+) 관계 | **실증 · 한국** |
| **왜 내린 날 더 깎나** | 오른 날 지갑이 열리고 내린 날 닫힌다(위와 동일). 동시에 슬플 때 **달콤한 것** 선택이 늘어난다 — Garg·Wansink·Inman (2007) *Journal of Marketing* | **실증 + 실험** |
| **왜 공모인가** | 슬픔을 줄이는 것은 구매가 아니라 **선택**이고 기제는 **통제감** — Rick 외 *JCP*, Garg (2019) | 실험 |
| 왜 저녁인가 | 주문의 **33%가 20~23시** | 기업 데이터 |
| ~~국내산 쌀가루~~ | 2026-09-18 원재료 표기 전수 확인 결과 **쌀가루는 국내산이 아니다.** 국내산 확인분은 벌꿀·난백액·우유 정도 | ⛔ **폐기** |

**남은 추론 한 칸** — *"주식 손실 → 막지 빵 구매"* 의 브랜드 단위 직접 관찰은 아직 없다.
발표에서 추론임을 밝히고, **오픈 후 2주간 코스피 일별 등락과 일별 주문 건수의 상관을 직접 재는 방법**을 같이 제시한다.

## 9. 수정안 — 2026-09-22~23에 **실행 완료**

아래는 9/18에 세운 계획이고, 지금은 전부 반영됐다. 하나는 실행하면서 **뒤집혔다**(2단계).

**거짓말을 없애는 것이 1순위다.**

쿠폰 방식은 **카페24 쿠폰이 회원 계정에 발급되는 구조**라 로그인이 없는 지금 쓸 수 없다.
그래서 **판매가 반영**으로 간다.

### 1단계 — 가격을 실제로 반영한다

```
15:30  국장 마감
   │  크론
   ▼
카페24 판매가 변경     setProductPrice() · 원가는 daily_plans에 저장
   ▼
빵장 화면 = 자사몰 가격     ← 거짓말 소멸
   ▼
24:00  크론 → 원가 복원
```

| 필요한 것 | 상태 |
|---|---|
| `setProductPrice()` | ✅ 있음 |
| 원가 저장 · 복원 기록 `daily_plans` | ✅ 있음 |
| `vercel.json` 크론 2개 | ✅ **2026-09-18 만듦** |
| `/api/cron/publish` · `/api/cron/restore` | ✅ **2026-09-18 만듦** |
| 안전 스위치 `PRICE_SYNC_ENABLED` | ✅ **꺼둔 상태** — 기업 승인 전에는 안 켠다 |

**전부 만들어 두었고 스위치만 꺼져 있다.** 승인이 오면 `PRICE_SYNC_ENABLED = true` 또는
`PRICE_SYNC=on` 환경변수 하나로 켜진다.

### 만들어 둔 것 (2026-09-18)

| | |
|---|---|
| `vercel.json` | 크론 2개. `30 6 * * 1-5`(=15:30 KST) · `10 15 * * 1-5`(=00:10 KST) |
| `/api/cron/publish` | 오늘 폭 계산 → 자사몰 판매가 변경 → 원가를 `daily_plans`에 저장. **휴장일은 건너뜀** |
| `/api/cron/restore` | `daily_plans`의 원가로 복원. 기록이 없으면 **아무것도 안 함**(추측으로 가격 안 씀) |
| `lib/priceSync.ts` | 두 동작의 실제 로직 + 안전 스위치 |
| `lib/cronAuth.ts` | `CRON_SECRET` 확인. **없으면 라우트가 잠긴다(503)** — 공개 URL이 가격 변경 버튼이 되면 안 되니까 |

**스위치가 꺼진 동안의 동작(dryRun)** — 크론이 돌아도 아무것도 바꾸지 않고
"무엇을 바꿀 것인가"만 돌려준다. 오늘 실제 결과:

```
dryRun=true · rate=0.3 · 코스피 +2.66%
  냉동생지 3종        21,000 → 14,700
  테트리스 브레드       11,000 →  7,700
  제로 무설탕 모닝롤      4,500 →  3,150
  글루텐프리 휘낭시에      3,800 →  2,660
  글루텐프리 스콘        3,800 →  2,660
  비건 잉글리시 머핀      1,500 →  1,050
```

**시각 계산 주의** — Vercel 크론은 UTC로 돈다. `15:10 UTC 월요일 = 00:10 KST 화요일`이라
그 순간의 KST 날짜는 되돌릴 그날이 아니다. 복원 라우트가 두 시간을 뒤로 밀어
막 끝난 그날(22:10 KST)의 날짜를 찾는다.

**같이 고친 버그** — `21000 × (1 - 0.3)`이 IEEE754에서 `14699.999999999998`이 되어
10원이 더 깎였다(30% 할인인데 14,690원). 90개 조합 중 8개가 어긋나 있었다.
`Math.round`를 먼저 거치게 네 곳을 고쳤다 — 화면·크론·관리자 반영·호가표.

### 2단계 — "예약"의 뜻을 바꾼다

판매가를 바꾸면 **전원이 같은 가격**이다. "선착순 30개 할인"이 성립하지 않는다.

| 새 의미 | 어떻게 | 선착순 |
|---|---|---|
| ~~한정 수량 = 카페24 재고~~ | ~~예약할 때 자사몰 재고를 깎아 31번째는 자사몰에서도 품절~~ | ⛔ **뒤집혔다** |
| **한정 수량 = 예약 건수** | `fills` 표가 센다. 자사몰 재고는 읽기만 한다 | **진짜가 된다** |

> ⛔ **왜 뒤집었나 (2026-09-22)**
> 예약할 때 자사몰 재고를 깎았더니, 손님이 실제로 사면 **카페24가 또 깎았다.**
> 빵 하나 팔고 재고가 2 줄어 30개를 풀면 15개에서 품절이다.
> 더 나쁜 쪽 — 예약만 쌓이면 재고가 0이 되는데 **재고 0이면 손님 화면에 품절이 뜬다.**
> 예약한 사람이 사러 갔더니 품절인 것이다(체험몰 실측).
>
> "31번째는 자사몰에서도 품절"이라는 목적은 `fills` 표가 이미 달성한다.
> 팔리지도 않은 재고를 막는 것은 **팔 수 있는 빵을 안 파는 것**이다.
> 주문 조회로 결제를 확인해 가차감을 되돌리는 정산이 붙으면 그때 다시 켠다.

## 10. 결정

발표까지 **12일**. 아래 셋이 막혀 있으면 화면이 더 나가도 서비스가 완성되지 않는다.

### ① 15:30~24:00 동안 자사몰 판매가를 API로 바꾸고 자정에 되돌려도 됩니까?

기업에 물을 것은 **사실상 이 한 문장**이다.
승인되면 *"싸다고 보여주고 정가로 보내는"* 상태가 끝난다.

**코드는 이미 준비돼 있다.** `PRICE_SYNC_ENABLED = true` 한 줄(또는 `PRICE_SYNC=on`)이면
15:30에 반영되고 자정에 복원된다. 그때까지는 꺼진 채로 계산만 한다.

### ② 공모 1위 빵을 실제로 출시 · 재입고할 수 있습니까?

안 되면 **공모는 넣지 않는 것이 맞다.** 1위가 안 나오면 서비스 신뢰가 끝난다.
신제품은 연 4회(이분이지)로 묶어 두었고, 나머지 20회는 이미 있는 제품의 재입고다.

### ③ 관심 담기 기록 — 만들었고, 고지 문구만 남았다

2026-09-19에 붙였다. 담는 순간 `watches`에 한 줄이 남고, 최근 7일 전환율
(체결 ÷ 관심)이 수요 보정을 정한다. 38% 구조의 비어 있던 한 축이 채워졌다.

남는 것은 기술이 아니라 **고지**다. 사람 단위로 세려고 서버가 난수 하나를
HttpOnly 쿠키로 발급한다(`bm_v`, 30일). 누구인지는 모르고 같은 브라우저인지만
아는 값이지만, 실서비스로 가면 개인정보처리방침에 쿠키 사용과 행동 기록을
적어야 한다. **기업에 물을 것은 "기록해도 됩니까"가 아니라 "이 문구를 어디에
넣습니까"다.**

한계 둘을 발표에서 밝힌다 — 쿠키를 지우면 같은 사람이 다시 한 명으로 잡히고,
전환율의 분자인 체결은 결제가 아니라 예약이다.
