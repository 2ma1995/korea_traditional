## 0. 왜 다시 넣는가

화면에서 뺀 이유는 아이디어가 아니라 **자리**였다. *"사용자 흐름이 분산돼서 무슨 서비스인지 모르겠다"* 는 지적을 받았을 때 같이 뺐고, 코드는 남겨 두었다.

다시 넣어야 하는 이유는 넷이다.

| | |
|---|---|
| 덱 8번 슬라이드 | 레시피 콘테스트 폐기의 **대체안**으로 이미 들어가 있다 |
| 사업자 베네핏 | 현직자: *"1팀은 사업자 베네핏 설득이 없었다"* → 출시 전 수요 데이터가 그 답 |
| 재방문 | 경쟁률이 매일 바뀐다 — 마감 뒤에도 화면이 움직이는 유일한 장치 |
| 절기 살리기 | 현직자: *"백로에 포도 띄우고 포도 상품이 없으면 그건 죽은 데이터"* |

### 그리고 근거가 하나 더 있다 — 통제감

> **「The benefits of retail therapy」** (Rick 외, *Journal of Consumer Psychology*)
> 슬픔을 줄이는 것은 구매 자체가 아니라 **choosing to buy — 선택하는 행위**다.
> **통제감(sense of control)** 회복이 기제다.
>
> **「Misery wants control」** (Garg 2019, *Australian Journal of Management*)
> 무력감이 슬픔–소비 관계를 매개하고, **선택이 통제감을 회복**시킨다.

공모는 **오늘의 구매보다 강한 통제감 장치**다.

```
오늘 구매   "싼 걸 골랐다"                  → 약한 선택
공모 청약   "내가 고른 빵이 실제로 나온다"   → 강한 선택
```

서비스 전체 근거(`기획_배경과_의사결정_기록.md` §2-3)와 **같은 기제**다. 별도의 곁가지가 아니라 같은 뿌리에서 나온 두 번째 층이다.

## 2. 혼합 규칙 — 회차 모드를 데이터가 정한다

가장 큰 위험은 **1위 빵이 실제로 나오지 않는 것**이다. 안 나오면 전부 거짓말이 된다. 그래서 기업 개발 부담을 연 4회로 묶는다.

```
회차 모드 판정 (절기마다)

  이분이지(춘분·하지·추분·동지)     →  신제품 공모     연 4회
  그 외 20개 절기                   →  재입고 공모     연 20회
```

이분이지는 절기 데이터에 이미 있다 — **황경이 90의 배수**인 네 절기다.

| 절기 | 황경 | 날짜 | 모드 |
|---|---:|---|---|
| 춘분 | 0 | 3/20 | 신제품 |
| 하지 | 90 | 6/21 | 신제품 |
| 추분 | 180 | 9/23 | 신제품 |
| 동지 | 270 | 12/22 | 신제품 |

절기를 임의로 고른 것이 아니라 **데이터에 있는 구분**(`longitude % 90 === 0`)을 쓴다. 발표에서 *"왜 이 네 개냐"* 에 답이 있다.

### 2-1. 재입고 공모 — 후보는 품절 상품

지금 **품절이 4종**이다. 이게 소재다.

| 품절 상품 | 정가 |
|---|---:|
| 마틸다 초코케이크 | 42,000원 |
| 달항아리 티라미수 | 15,000원 |
| ZERO 카스테라 | 12,000원 |
| 대만식 샌드위치 | 2,400원 |

후보는 **정가 높은 순 3종**. 1위가 재입고되면 품절 목록에서 빠지고 다음 상품이 자동으로 올라온다 — 목록이 스스로 돈다.

> 품절 상품은 `/api/stock`이 자사몰에서 실시간으로 받아온다. 손으로 관리하지 않는다.

**품절이 3종 미달이면** 모자란 자리를 절기 제철 후보로 채운다. 회차에 후보가 비는 경우를 만들지 않는다.

### 2-2. 신제품 공모 — 후보는 절기 제철 재료

현재 `lib/ipo.ts`의 방식을 그대로 쓴다.

- 후보 1 = 절기 데이터의 `productIdea` (근거가 적혀 있는 것)
- 후보 2·3 = `productIdea`에 안 쓰인 제철 재료 + 막지 제품 형태

### 2-3. 두 모드의 말이 다르다

| | 재입고 공모 | 신제품 공모 |
|---|---|---|
| 배너 | **재상장 공모** | **신규 상장 공모** |
| 질문 | "무엇을 먼저 다시 들여올까요?" | "다음 절기엔 어떤 빵이 좋을까요?" |
| 기업 부담 | 생산만 | 개발 + 생산 |
| 약속 강도 | **지킬 수 있다** | 기업 확인 필요 |

## 3. 청약 자격 — 구매가 증거금이다

무료 탭 한 번이면 그것은 **투표**지 공모가 아니다. 진짜 공모는 증거금을 건다.

```
오늘 빵을 산다  →  청약권 1장  →  다음 빵을 고를 권리
```

얻는 것이 셋이다.

1. **은유가 성립한다** — "공모주"라고 부를 수 있다
2. **구매 동기가 하나 더 붙는다** — 오늘 사면 다음을 정할 수 있다
3. **허수가 없다** — 사업자가 얻는 것이 실구매자 수요 데이터다

### 3-1. 회원 없이 어떻게 검증하나

이 서비스에는 로그인이 없다. 그래서 **서버가 발급하는 쿠키**로 검증한다.

```
POST /api/fill  성공
  → Set-Cookie: bm_bid=<서울 날짜>; HttpOnly; SameSite=Lax; Max-Age=86400

POST /api/ipo
  → 쿠키 bm_bid 가 오늘 날짜인지 확인
  → 청약 성공 시 소진 (bm_bid 삭제 + bm_bid_used=<날짜> 기록)
```

`HttpOnly`라 페이지 스크립트로는 못 만든다. 서버만 발급한다.

**한계 — 발표에서 밝힌다.** 쿠키를 지우고 다시 구매하면 청약권을 또 얻는다. 다만 구매가 **선착순 한정 수량(30개)** 이라 남용에 실제 비용이 든다. 정식 방어는 회원 체계가 붙은 뒤다.

이전 방식(`localStorage`로만 1인 1청약)보다는 한 단계 위다 — 그건 브라우저 저장소를 지우면 끝이었고 서버는 아무것도 못 막았다.

## 4. 화면 자리 — 탭이 아니라 스크롤 순서

별도 탭으로 빼면 처음 온 사람은 영영 못 본다. 그게 지난번에 뺀 이유이기도 하다.

```
MARKET   지금 국장이 어떤가          ← 히어로 · 차트
TODAY    오늘 살 수 있는 빵          ← 할인 목록
MY       내가 가진 것                ← 포트폴리오
NEXT     다음에 나올 빵              ← 공모  ★ 여기 (맨 아래)
```

**시간 순서가 곧 화면 순서**가 되어 흐름이 흩어지지 않는다. 오늘 살 것 → 내 것 → 다음에 나올 것으로 이어진다.

> 공모를 포트폴리오 **아래**에 둔 이유. 청약은 오늘 빵을 산 사람만 할 수 있으니(§3),
> 구매·관심을 다 지난 뒤에 나오는 것이 순서에 맞다. 처음 온 사람에게 먼저 보여줄 것은
> 오늘 살 수 있는 빵이고, 공모는 그 다음 방문의 이유다.

### 4-1. 상태별 화면

| 상태 | NEXT 섹션이 보여주는 것 |
|---|---|
| 오늘 구매 전 | 후보 3종 + 경쟁률. 버튼은 **"오늘 빵을 사면 청약할 수 있어요"** (비활성) |
| 청약권 있음 | 버튼 **"청약하기"** 활성 |
| 청약 완료 | 내 후보에 **"내 청약 ✓"**, 나머지는 비활성 |
| 장 마감 후 | 경쟁률만. 마감까지 D-N |

오늘 안 산 사람에게도 후보와 경쟁률은 보인다 — **구매 동기를 만드는 자리**라서 가려선 안 된다.
화면 자체를 구매자에게만 보여주면 "사면 참여할 수 있다"는 동기가 생기지 않는다.

### 4-2. CJM — 여기까지 어떻게 도달하는가

공모를 만들고 나서 동선을 짚어 보니 **끊긴 곳이 셋** 있었다. 셋 다 막았다.

| # | 어디서 | 문제 | 조치 |
|---|---|---|---|
| 1 | 구매 **전** | 버튼이 잠겨 있으니 맨 아래까지 스크롤할 이유가 없다 | NEXT 헤드에 **청약권 상태 한 줄** — 왜 잠겼는지, 어떻게 열리는지 |
| 2 | 구매 **직후** | 시트가 *"자사몰에서 결제하기 ↗"* 로 **외부로 보냈다.** 청약권이 생긴 것을 아무도 몰랐다 | 시트에 **`🗳 청약권 1장이 생겼어요`** 버튼 → 시트 닫고 `#next`로 스크롤 |
| 3 | 헤더 | `빵장 / 절기 / 스물네 절기 / MY` — NEXT가 없어 직접 갈 수 없다 | 헤더에 **`NEXT`** 추가 |

2번이 핵심이다. **구매가 체결된 그 순간이 공모로 넘어가는 유일한 전환 시점**이고, 그때 사용자를 자사몰로 내보내고 있었다.

**고친 뒤 여정**

```
① 대문 애니메이션 (3.4초 · 같은 날 재방문은 스킵)
② MARKET   국장 등락 · 차트 · 오늘 몇 %
③ TODAY    할인 빵 → 클릭 → 시트 → 구매
              │
              └─ 🗳 "청약권 1장이 생겼어요 → 다음 빵 고르기"   ← 전환
④ MY       내 포트폴리오
⑤ NEXT     청약 → "내 청약 ✓"
              │
              └─ 다음 절기까지 경쟁률 보러 재방문            ← 재방문 루프
```

구매 전 사용자는 ⑤에서 *"오늘 빵을 사면 청약권 1장이 생깁니다"* 를 보고 ③으로 되돌아간다 — 공모가 구매 동기가 되는 방향도 열어 둔다.

## 5. 회차 생애

```
절기 15일 전   공모 오픈 · 후보 3종 공개
매일           경쟁률 갱신 (마감 뒤에도 변한다 — 재방문 이유)
절기 당일      마감 · 1위 확정
그 다음        1위 상장(재입고 또는 출시) · 청약자 쿠폰
```

절기 간격이 약 15일이라 **한 회차가 끝나면 바로 다음 회차**가 열린다. 빈 기간이 없다.

## 6. DB

`0006_ipo.sql`은 **아직 실행하지 않았다.** 실행 전에는 서버 메모리 폴백으로 돌고, 화면이 그 사실을 표시한다(`live: false`).

기존 스키마에 한 열을 더한다 — 어느 모드의 회차였는지 남겨야 나중에 "재입고 공모와 신제품 공모 중 어느 쪽 참여가 높았나"를 답할 수 있다.

```sql
alter table ipo_bids add column if not exists mode text;   -- 'restock' | 'new'
```

개인 식별 값은 계속 저장하지 않는다. 회차·후보·모드만 남긴다.

## 8. 왜 이전 방식보다 나은가

| | 이전 | 이번 |
|---|---|---|
| 자리 | 별도 탭 → 아무도 안 봄 | NEXT 섹션 → 스크롤에 걸림 |
| 후보 | 항상 신제품 → 기업이 못 지킴 | 평소 재입고 → **지킬 수 있음** |
| 자격 | 누구나 무료 → 투표 | 오늘 구매자 → **공모** |
| 중복 방어 | localStorage (서버 무방비) | 서버 발급 쿠키 |
| 근거 | 현직자 제안 | 현직자 제안 **+ 통제감 연구** |

## 9. 기업 확인 필요 목록

화면에 약속으로 쓰기 전에 받아야 하는 것들이다.

| # | 확인할 것 | 없으면 |
|---|---|---|
| 1 | **1위 빵을 실제로 출시·재입고할 수 있는가** | 공모 전체가 성립하지 않는다 |
| 2 | 신제품 개발이 **연 4회** 가능한가 | 이분이지도 재입고 공모로 |
| 3 | 청약자 쿠폰을 **발급할 수 있는가**(할인율·수량) | "쿠폰" 문구를 빼고 "먼저 알림"으로 |
| 4 | 품절 4종의 **재입고 계획·시점** | 재입고 공모의 약속 강도가 낮아진다 |
| 5 | 회차 후보를 기업이 직접 넣을 관리자 화면 필요 여부 | 절기 데이터 자동 생성으로 유지 |

**1번이 전제다.** 나머지는 조정 가능하지만 1번이 안 되면 이 기능은 넣지 않는 게 맞다.
